# mm.c 개선 계획 (Improvement Plan)

`./test` 로 측정한 현재 상태를 기준으로, 이용률(util)과 처리량(throughput)을 함께 올리기 위한 단계별 계획입니다.
**한 번에 한 단계씩** 바꾸고, 단계마다 `./test` 로 측정해서 효과가 확인된 것만 남깁니다.

> 표기: **[측정]** 은 실제로 돌려서 나온 값, **[추정]** 은 아직 측정하지 않은 예상입니다.

---

## 0. 현재 상태 (기준선)

### 실제 `mm.c` 의 상태
- `find_fit`: **best-fit 적용됨**
- `mm_realloc`: **아직 변경 없음.** 작성 중인 코드(`oldptr` 를 `mm_free` 하지 않고, 줄일 때도 옛 크기만큼 복사)라서 지금은 realloc trace 2개가 `mm_realloc failed`(메모리 부족)로 실패하고 점수가 계산되지 않습니다.
- realloc **제자리 확장은 한 번도 적용한 적이 없습니다.** 아래 "시험만 해 본 실험" 은 임시 복사본에서만 돌린 결과입니다.

### 기준선: best-fit + 올바른 기본 realloc (새로 할당 → 복사 → free) [측정, 맥 임시 복사본, 5회]
```
점수 = 이용률 × 60 + min(1, 처리량 ÷ 600 Kops) × 40
```
| 항목 | 값 | 점수 | 남은 점수 |
|---|---|---|---|
| 이용률 | 75% | 45 / 60 | 약 15 (trace 특성상 100% 는 어려움) |
| 처리량 | 약 237 Kops | 약 16 / 40 | **약 24** |
| 합계 | | **60~61** | |

→ 점수가 더 남은 쪽은 **처리량**입니다.

### trace별 이용률 / 처리량 [측정]
| trace | 이용률 | 처리량 | 비고 |
|---|---|---|---|
| amptjp, cccp, cp-decl, expr | 99~100% | 676~1044 Kops | 개선 여지 거의 없음 |
| coalescing | 66% | | 힙 확장 방식 문제로 추정 → **1단계** |
| random, random2 | 95~96% | 401~433 Kops | |
| binary | 55% | **86 Kops** | 느리고 이용률도 낮음 → **2단계** |
| binary2 | 51% | **99 Kops** | 느리고 이용률도 낮음 → **2단계** |
| realloc | 31% | 304 Kops | 기본 realloc 의 한계 |
| realloc2 | 30% | 7565 Kops | 기본 realloc 의 한계 |

처리 시간의 대부분(80% 이상)을 `binary`, `binary2` 두 trace가 씁니다. 원인은 `find_fit` 이 **할당된 블록까지 힙 전체를 훑기** 때문입니다.

### 실제로 적용했던 이력 (사용자 코드) [측정]
| 버전 | 평균 이용률 | 처리량 | 점수 |
|---|---|---|---|
| first-fit + 기본 realloc | 74% | 244 Kops | 61 |
| best-fit + 기본 realloc | 75% | 약 237 Kops | 60~61 |

### 시험만 해 본 실험 (임시 복사본에서만 측정, **mm.c 에는 적용 안 함**) [측정]
realloc 에 "제자리 확장"을 넣어 본 결과입니다. 단계 1~3 과 별개로, 나중에 적용 여부를 정할 수 있는 후보입니다.

| 실험 | 평균 이용률 | 처리량 | 점수 | realloc / realloc2 이용률 |
|---|---|---|---|---|
| A. 뒤 블록과만 합치기 (+ 힙 끝 확장) | 75% | 약 264 Kops | 62~63 | 28% / 34% |
| B. A + 앞 가용 블록까지 합쳐 `memmove` | **77%** | 약 264 Kops | **63~64** | **41% / 45%** |

- 처리량 상승은 realloc 이 복사 없이 처리되기 때문이고, 이용률 상승은 B 에서만 나타났습니다.
- B 를 적용할 때는 `grow_in_place` 가 **옮겨진 주소를 반환**하므로, `mm_realloc` 이 `return ptr;` 이 아니라 그 반환값을 돌려줘야 합니다 (처음 만들 때 이 실수로 오류가 났었습니다).

### 공통 진행 규칙
- 단계를 시작하기 전에 `mm.c` 를 백업합니다 (예: `cp mm.c mm.c.step0.bak`).
- 각 단계 후 `./test` 를 **5번** 돌려 중앙값을 기록합니다 (처리량은 실행마다 흔들립니다).
- 완료 기준: ① 11개 trace 모두 통과 ② 이전 단계보다 점수가 **내려가지 않음** ③ 아래 기록표 작성.
- 기본 trace 11개가 건드리지 않는 경로(예: realloc 의 힙 끝 확장)는 **직접 만든 작은 trace** 로 따로 검증합니다.

## 1단계. 힙 확장 방식 고치기

**목표:** `coalescing` trace 이용률 66% 개선. 난이도 **쉬움**, 위험 **낮음**.

### 문제 [추정]
`mm_malloc` 은 맞는 블록이 없으면 `MAX(asize, CHUNKSIZE)` 만큼 힙을 늘립니다.
`coalescing` trace 는 4095바이트(블록 4104)를 반복해서 쓰는데, 초기 힙은 4096 이라 첫 블록도 못 담습니다.
그래서 매번 4104 를 새로 늘리고, 힙 끝의 남는 가용 블록은 활용하지 못해 힙이 필요 이상으로 커집니다.
(이 계산은 `gen_coalescing.pl` 을 읽고 추정한 것이며, 힙 크기를 직접 찍어 확인하지는 않았습니다.)

### 변경 내용
- 힙 끝(에필로그 바로 앞) 블록이 **가용이면** `asize - 그 블록 크기` 만큼만 늘립니다.
  ```
  [... 가용 4096][에필로그]  →  요청 4104  →  8만 늘림  →  [가용 4104][에필로그]
  ```
- 끝 블록이 가용이 아니면 기존처럼 `MAX(asize, CHUNKSIZE)`.
- 마지막 블록 찾기: 에필로그 bp = `mem_heap_hi() + 1`, 그 앞 블록은 `PREV_BLKP(에필로그 bp)`.
- 함께 검토: `mm_init` 의 초기 확장 크기(`CHUNKSIZE`)를 줄여 보는 실험.

### 장점
- 코드 변경이 작고 되돌리기 쉽습니다.
- 힙이 줄면 `coalescing` 이용률이 크게 오를 것으로 예상합니다 [추정: 99% 근처, 평균 +3%p].

### 단점 / 위험
- 필요한 만큼만 늘리면 `mem_sbrk` 호출이 늘 수 있습니다 (이 lab 의 `mem_sbrk` 는 포인터만 올려서 비용은 작음).
- 너무 딱 맞게 늘리면 다음 요청 때 또 늘려야 합니다. 효과가 trace에 따라 달라질 수 있어서 `CHUNKSIZE` 값 변경과 함께 측정이 필요합니다.
- 다른 trace 의 이용률이 내려가면 적용하지 않습니다.

### 검증
`./test` 11개 통과 + `coalescing` 이용률 변화 확인. 힙 크기를 임시로 출력해서 추정이 맞는지 확인.

## 2단계. Segregated free list + 4바이트 오프셋 포인터

**목표:** **처리량**을 크게 올림 (`binary`, `binary2` 가 핵심). 난이도 **어려움**, 위험 **높음**.

### 문제 [측정]
`find_fit` 이 힙 맨 앞부터 모든 블록을 훑습니다. 블록이 많은 trace 에서 `malloc` 한 번이 O(블록 수) 입니다.

### 변경 내용

**(a) 가용 블록만 크기 구간별 리스트로 관리**
```
구간 0: 16~31      → [가용]↔[가용]↔...
구간 1: 32~63      → [가용]↔...
구간 2: 64~127     → ...
 ...
구간 k: 2^(k+4)~   → ...
```
- `find_fit`: 요청 크기가 속한 구간부터 시작해 더 큰 구간으로 올라가며 **첫 번째로 맞는 블록**을 씁니다.
- 가용 블록은 free 될 때(`coalesce` 결과), 힙을 늘릴 때(`extend_heap`), 분할 후 남은 조각(`place`)에서 리스트에 들어가고, 할당될 때와 합쳐질 때 빠집니다.
- (realloc 에 제자리 확장을 적용했다면) 그 경로에서도 **합쳐지는 이웃 가용 블록을 리스트에서 빼야** 합니다.

**(b) 포인터를 4바이트 오프셋으로 저장 (4번 항목)**
- 가용 블록 안에 prev/next 를 저장합니다. 64비트 포인터(8바이트)를 쓰면 가용 블록 최소 크기가 16 → 24 로 커져서 작은 요청마다 공간을 더 씁니다.
- 힙 시작(`mem_heap_lo()`) 기준의 4바이트 오프셋으로 저장하면 최소 블록을 **16바이트**로 유지할 수 있습니다 (최대 힙 20MB < 4GB).
  ```
  가용 블록: [헤더 4][prev 오프셋 4][next 오프셋 4][푸터 4] = 16바이트
  ```
- 오프셋 0 은 "없음(NULL)" 으로 약속합니다 (힙 맨 앞은 패딩이라 유효한 블록이 올 수 없음).

**(c) 구간별 리스트 head 저장 위치 — 규칙 확인 필요**
- 원본 CS:APP 안내서에는 "전역/static **배열** 금지(스칼라 전역변수만 허용)" 규칙이 있습니다. 이 폴더의 README 에는 해당 문구가 없어서 **과제 공지에서 확인이 필요**합니다.
- 안전한 방법: head 들을 **힙 안**(초기 패딩 뒤 20워드 정도)에 저장하고 오프셋으로 접근합니다.

### 장점
- 가용 블록만 탐색하므로 `malloc` 비용이 크게 줄어듭니다 [추정: 처리량 대폭 상승].
- `binary` trace: 448바이트 가용 블록 2000개가 512바이트 요청의 구간(512~)에 없어서 탐색 없이 바로 힙 확장으로 갑니다 [추정]. 단순 explicit list 는 이 가용 블록 2000개를 매번 훑어서 이득이 작습니다.
- 구간 안 first-fit 은 best-fit 과 비슷한 이용률을 내는 것으로 알려져 있습니다 [일반적인 경험칙, 이 코드에서는 미측정].
- 오프셋 방식으로 최소 블록 16바이트를 유지해 이용률 손해를 피합니다.

### 단점 / 위험
- 구현량이 큽니다: 리스트 삽입/삭제, 구간 계산, `coalesce`, `place`, `extend_heap`, `realloc` 전부를 고쳐야 합니다.
- 리스트 포인터 오류는 **조용히 힙을 망가뜨려** 원인 찾기가 어렵습니다.
  → 대응: 힙 일관성 검사 함수(`mm_check`)를 먼저 만듭니다. 검사 항목: 가용 블록이 모두 리스트에 있는지, 리스트의 블록이 모두 가용인지, 연속된 가용 블록이 없는지, 블록이 올바른 구간에 있는지.
- 오프셋 ↔ 포인터 변환 매크로가 늘어 코드가 복잡해집니다.
- 처리량은 오르지만 이용률은 거의 변하지 않거나 조금 내려갈 수 있습니다.

### 권장 진행 순서 (2단계 안에서)
1. `mm_check` 작성 (기존 구조에서도 동작하게)
2. 오프셋 매크로와 리스트 삽입/삭제만 추가, 아직 `find_fit` 은 그대로
3. `find_fit` 을 리스트 기반으로 교체 → `./test`
4. `realloc` 경로의 리스트 갱신 확인 → 직접 만든 trace 로 검증

### 검증
11개 통과 + `mm_check` 통과 + `binary`, `binary2` Kops 변화 + 평균 이용률이 1단계 결과보다 내려가지 않는지.

## 3단계. 할당된 블록의 푸터 제거

**목표:** 블록당 4바이트를 줄여 **이용률**을 조금 더 올림. 난이도 **중간~어려움**, 위험 **높음**. 2단계 후에 진행.

### 변경 내용
- 푸터는 **가용 블록에만** 둡니다 (합칠 때 이전 블록 크기를 알기 위한 용도).
- 이전 블록이 할당됐는지를 **헤더의 비트 하나**에 저장합니다.
  ```
  헤더: [ 크기 (상위 비트) | 0 | prev_alloc(0x2) | alloc(0x1) ]
  ```
- 할당 블록: `[헤더 4][payload ...]` → `asize = align8(요청 + 4)`, 최소 16바이트 (payload 최대 12바이트).
- `PREV_BLKP` 는 **이전 블록이 가용일 때만** 쓸 수 있습니다 (푸터가 있을 때).

### 장점
- 작은 블록이 많은 trace 에서 이용률이 오릅니다 [추정: 평균 1~3%p, 이미 99% 인 trace 는 변화 작음].
- 요청 12바이트 이하가 16바이트 블록에 들어갑니다 (지금은 8바이트까지만).

### 단점 / 위험
- `prev_alloc` 비트를 **모든 곳**에서 일관되게 유지해야 합니다: `mm_init`, `extend_heap`(에필로그), `place`(분할), `coalesce`, `mm_free`, `realloc` 의 모든 경로, 리스트 삽입/삭제.
- 비트 하나를 놓치면 가끔만 터지는 버그가 됩니다. → `mm_check` 에 `prev_alloc` 일치 검사를 추가합니다.
- `realloc` 의 옛 payload 크기 계산이 `GET_SIZE - DSIZE` 에서 `GET_SIZE - WSIZE` 로 바뀝니다 (복사 길이 계산 수정 필수).
- 이득 대비 위험이 큰 단계라서, 1~2단계 결과를 보고 **할지 말지 결정**합니다.

### 검증
11개 통과 + `mm_check` 통과 + 이용률 변화 확인. 이득이 1%p 미만이면 되돌립니다.

## 이 계획에 넣지 않은 것
